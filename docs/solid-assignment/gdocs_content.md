## ۱. مشخصات نرم‌افزار فعلی ژتون و تاریخچه تغییرات و تکامل معماری

این تمرین بر مبنای آخرین نسخه فعال نرم‌افزار **«ژتون» (Zheton)** که روی گیت‌هاب در حال توسعه است تدوین شده است. سیستم به عنوان یک دستیار مالی شخصی و اول‌محلی (Local-First) پیامک‌های بانکی کشور را بدون نیاز به سرور مرکزی پردازش می‌کند، ارزش دارایی‌ها را در برابر تورم با طلا می‌سنجد و سقف خرج امن روزانه را حساب می‌کند.

### تغییرات و سیر تکامل نسبت به نسخه‌های اولیه:
1. **تغییر برند و ادغام در ۴ تب اصلی (طبق ADR 0007):**
   صفحات متعدد و پراکنده اولیه در ۴ تب متمرکز ادغام شدند: «داشبورد» (نقدینگی، خرج امن و سپر تورم)، «بازار» (مظنه طلا، سکه و رادار حباب)، «حساب‌ها» (کارت‌های بانکی شتاب، اقساط BNPL و چک صیادی) و «دفترکل و تحلیل» (گردش تراکنش‌ها و قاعده ۵۰/۳۰/۲۰).
2. **افزودن موتور خرج امن روزانه (`SafeSpendEngine`):**
   محاسبه پویا و غیرخطی سقف مجاز مخارج امروز با تفکیک تعهدات بدهی و اعمال ضریب مصرف روزهای پایان هفته در ایران (پنج‌شنبه ۱٫۴۰ و جمعه ۱٫۲۵).
3. **تکامل معماری پایگاه‌داده به سیستم دوپایگاه‌داده‌ای:**
   تفکیک فضای ذخیره‌سازی به `durable.db` (پیامک‌های خام، قواعد و تصمیمات ماندگار کاربر) و `derived.db` (خروجی‌های محاسباتی دفترکل). با این تغییر، به‌روزرسانی پارسر یا اصلاح الگوریتم‌ها بدون ریسک پاک شدن اصلاحات کاربر و بدون نیاز به دسترسی مجدد به اینباکس انجام می‌شود.
4. **رهگیری بدهی‌های نوین اعتباری و اقساط (`Commitment`):**
   پشتیبانی از سرویس‌های الان بخر بعداً پرداخت کن (اسنپ‌پی، دیجی‌پی)، چک‌های صیادی و وام‌های بانکی، همراه با محاسبه سود روانی کاربر ناشی از فرسایش ارزش واقعی اقساط در تورم.
5. **ارتقای اعتبارسنجی کارت‌ها و شبا:**
   تشخیص خودکار نام بانک از ۶ رقم اول کارت، اعتبارسنجی الگوریتم Luhn برای کارت و استاندارد ISO-7064 برای شماره شبا، و پایش حساب‌های راکد با عدم فعالیت بیش از ۴۵ روز.

## ۲. معرفی ۵ کلاس اصلی سیستم (پاسخ سوال‌های ۱، ۲ و ۳)

### ۱. کلاس BankAccount (موجودیت حساب و کارت بانکی)
* **نقش در سیستم:** موجودیت دامنه (Domain Entity)
* **مسئولیت کلاس:**
  این کلاس وظیفه نگهداری و مدیریت اطلاعات حساب یا کارت بانکی کاربر (مانند شماره کارت، شماره شبا، بانک صادرکننده و مانده حساب) را بر عهده دارد. همچنین وضعیت کارت را اعتبارسنجی می‌کند تا مطمئن شود مانده اعلام‌شده بر اساس پیامک رسمی بانک ثبت شده و حساب‌های راکدی که بیش از ۴۵ روز تراکنشی نداشته‌اند را مشخص می‌نماید.
* **ویژگی‌های اصلی (Attributes):**
  * `bank: Bank` — مشخصه بانک صادرکننده از شبکه شتاب (مثلاً ملی، سامان، بلو، تجارت)
  * `mask: String` — چهار رقم انتهای کارت برای انطباق سریع با پیامک‌های دریافتی
  * `balance: Double` — آخرین مانده ثبت‌شده حساب به تومان
  * `fullPan: String` — شماره کامل ۱۶ رقمی کارت بانکی
  * `sheba: String` — شماره ۲۴ رقمی شبا به همراه شناسه IR
  * `anchored: Boolean` — نشان‌دهنده تثبیت مانده حساب با پیامک قطعی بانک
  * `updatedAt: Long` — زمان ثبت آخرین تراکنش موفق این حساب
* **عملیات و متدهای کلیدی (Methods):**
  * `isDormant(nowEpochMs: Long): Boolean` — بررسی راکد بودن حساب بیش از ۴۵ روز
  * `trusted(): Boolean` — تأیید قطعی بودن موجودی حساب بر اساس داده‌های موثق بانکی
  * `validateLuhn(): Boolean` — اعتبارسنجی ارقام کارت بانکی با الگوریتم Luhn جهت جلوگیری از خطای تایپی
  * `bankFa(): String` — برگرداندن نام فارسی رسمی بانک برای نمایش در رابط کاربری

### ۲. کلاس BankSms (شیء مقدار / مدل پیامک بانکی)
* **نقش در سیستم:** شیء مقدار (Value Object)
* **مسئولیت کلاس:**
  پیامک‌های دریافتی از بانک‌ها متن‌های نامنظم و متفاوتی دارند. این کلاس اطلاعات تمیز و پالایش‌شده یک پیامک تراکنشی (مانند مبلغ، جهت واریز یا برداشت، کارمزد، مانده جدید و نام فروشگاه) را نگهداری می‌کند تا بقیه بخش‌های برنامه بدون درگیر شدن با متن خام پیامک، با داده‌های تمیز و ساخت‌یافته کار کنند.
* **ویژگی‌های اصلی (Attributes):**
  * `bank: Bank` — بانک صادرکننده پیامک (تشخیص داده شده از روی سرشماره)
  * `sender: String` — سرشماره‌ای که پیامک از آن در گوشی دریافت شده
  * `amountRial: Long?` — مبلغ تراکنش به ریال
  * `balanceRial: Long?` — مانده حساب بعد از تراکنش به ریال
  * `feeRial: Long?` — مبلغ کارمزد کسرشده توسط بانک
  * `merchant: String` — نام فروشگاه، پذیرنده یا مقصد تراکنش
  * `channel: Channel` — کانال انتقال (کارت‌خوان، خودپرداز، پایا، ساتنا، کارت‌به‌کارت)
  * `delta: Double?` — تغییر خالص حساب (با علامت مثبت برای واریز و منفی برای برداشت)
* **عملیات و متدهای کلیدی (Methods):**
  * `empty(): Boolean` — تشخیص پیامک‌های تبلیغاتی یا غیرمالی بانک که حاوی گردش پول نیستند
  * `isDeposit(): Boolean` — تشخیص واریز بودن تراکنش مالی
  * `toDerivedTxn(): Txn` — تبدیل پیامک پردازش‌شده به ردیف استاندارد قابل ثبت در جدول دفترکل
  * `cleanMerchantName(): String` — پیرایش علائم زائد از نام پذیرنده برای گزارش‌گیری مرتب‌تر

### ۳. کلاس Commitment (موجودیت تعهدات و اقساط مالی)
* **نقش در سیستم:** موجودیت بدهی و تعهدات (Liability Entity)
* **مسئولیت کلاس:**
  در مدیریت مالی روزمره، اقساط وام‌ها، خریدهای قسطی اعتباری (مانند اسنپ‌پی و دیجی‌پی) و چک‌های صیادی اهمیت بالایی دارند. مسئولیت این کلاس، ثبت و پیگیری مانده بدهی‌ها، تعداد اقساط پرداخت‌شده، تاریخ سررسید قسط بعدی، و از همه مهم‌تر محاسبه اثر فرسایشی تورم روی اقساط آینده است تا مشخص شود ارزش واقعی بدهی کاربر در ماه‌های آینده چقدر کاهش می‌یابد.
* **ویژگی‌های اصلی (Attributes):**
  * `id: String` — شناسه یکتا برای هر تعهد مالی
  * `title: String` — عنوان قسط یا بدهی (مثلاً «قسط لپ‌تاپ»)
  * `provider: String` — تسهیلات‌دهنده (اسنپ‌پی، دیجی‌پی، بانک سامان و...)
  * `kind: CommitmentKind` — نوع تعهد (وام بانکی، خرید اعتباری BNPL، چک صیادی)
  * `totalAmountRial: Long` — کل مبلغ تعهد مالی به ریال
  * `remainingAmountRial: Long` — مبلغ باقیمانده از بدهی
  * `installmentCount: Int` — تعداد کل اقساط
  * `paidInstallmentCount: Int` — تعداد اقساطی که تا امروز پرداخت شده است
  * `nextDueTimestamp: Long` — تاریخ و زمان سررسید قسط بعدی
* **عملیات و متدهای کلیدی (Methods):**
  * `progressPercent(): Float` — محاسبه درصد پیشرفت پرداخت اقساط
  * `nextDueDays(): Int` — محاسبه تعداد روزهای مانده تا تاریخ سررسید قسط بعدی
  * `discountedPresentValueToman(months: Int): Long` — تنزیل ارزش ریالی قسط‌های آینده با نرخ تورم و به دست آوردن ارزش واقعی آن در زمان حال
  * `inflationReliefToman(months: Int): Long` — محاسبه سود روانی کاربر حاصل از فرسایش ارزش بدهی در اثر تورم

### ۴. کلاس SafeSpendEngine (سرویس دامنه محاسبات هوشمند بودجه)
* **نقش در سیستم:** سرویس دامنه (Domain Service)
* **مسئولیت کلاس:**
  این کلاس مغز متفکر پروژه برای پاسخ به سؤال کلیدی «امروز چقدر می‌توانم خرج کنم؟» است. این کلاس با کاتلین خالص نوشته شده و هیچ وابستگی به فریم‌ورک اندروید یا دیتابیس ندارد. وظیفه آن این است که با دریافت کل موجودی نقد کاربر، کسر تعهدات و اقساط نزدیک، و اعمال ضریب‌های الگوی مصرف در روزهای هفته ایران (خرج بیشتر در پنج‌شنبه و جمعه)، سقف خرج امن امروز را حساب کند و در صورت سرعت بالای خرج، روز اتمام بودجه را پیش‌بینی کند.
* **ویژگی‌های اصلی (Attributes):**
  * `WEEKEND_SURGE_WEIGHT = 1.40` — ضریب وزنی افزایش مخارج در روز پنج‌شنبه
  * `FRIDAY_SURGE_WEIGHT = 1.25` — ضریب مصرف در روز جمعه
  * `BASE_DAY_WEIGHT = 1.00` — ضریب پایه روزهای عادی (شنبه تا چهارشنبه)
  * `MIN_BUFFER_RATIO = 0.10` — درصد ذخیره احتیاطی اضطراری که نباید خرج شود
* **عملیات و متدهای کلیدی (Methods):**
  * `calculatePacing(cash: Long, liabilities: Long, cycleDays: Int): PacingDecision` — فرمول اصلی تعیین عدد خرج امن روزانه به همراه شاخص شتاب بودجه
  * `dayOfWeekWeight(dayOfWeek: Int): Double` — تعیین ضریب وزنی مخارج بر اساس روزهای تقویم شمسی
  * `iranianDayOfWeek(tehranDay: Long): Int` — تبدیل روز تقویمی به شماره روز هفته در ایران (شنبه = ۱ تا جمعه = ۷)
  * `projectExhaustionDay(balance: Long, burnVelocity: Double): Int?` — تخمین روزی از ماه که در صورت ادامه الگوی فعلی، پول کاربر تمام خواهد شد

### ۵. کلاس LedgerEngine (سرویس هماهنگ‌کننده پایگاه‌داده و دفترکل)
* **نقش در سیستم:** سرویس هماهنگ‌کننده (Application Orchestrator)
* **مسئولیت کلاس:**
  این کلاس وظیفه هماهنگ‌سازی تراکنش‌ها با پایگاه‌داده محلی (Room) را بر عهده دارد. مسئولیت اصلی آن مدیریت قفل‌های همزمانی (Mutex) برای جلوگیری از تداخل فرآیندهای پس‌زمینه با دستورات کاربر، استخراج و بازسازی دفترکل از روی پیامک‌ها، و ثبت قواعد دسته‌بندی خودکار است.
* **ویژگی‌های اصلی (Attributes):**
  * `durable: DurableDb` — پایگاه‌داده داده‌های ماندگار کاربر (پیامک‌های خام، دسته‌بندی‌ها و قوانین قطعی)
  * `derived: DerivedDb` — پایگاه‌داده موقت و محاسباتی دفترکل که در صورت لزوم به راحتی بازسازی می‌شود
  * `mutex: Mutex` — قفل همزمانی کوروتین‌ها جهت تضمین این‌که دو پردازش همزمان اطلاعات دفترکل را دستکاری نکنند
  * `extraBankNumbersProvider: () -> Map<String, List<String>>` — ارائه‌دهنده انتزاعی سرشماره‌های بانکی جدید
* **عملیات و متدهای کلیدی (Methods):**
  * `withLedgerLock(block: suspend () -> T): T` — اجرای ایزوله عملیات حساس مالی در نخ ورودی/خروجی (Dispatchers.IO)
  * `rederive(extraNumbers: Map): Int` — بازتولید کامل تراکنش‌های دفترکل از روی پیامک‌های ذخیره‌شده
  * `categorise(entry: LedgerEntry, categoryId: String, always: Boolean)` — دسته‌بندی یک تراکنش و ذخیره قاعده دائمی اگر کاربر خواسته باشد همه تراکنش‌های مشابه هم علامت بخورند
  * `loadSession(durable: DurableDb): Session` — بارگذاری سشن فعال برای ثبت و اعمال تغییرات گروهی

## ۳. بررسی اصول SOLID رعایت‌شده در معماری پروژه ژتون (پاسخ سوال ۴)

در طراحی این پروژه، اصول زیر از اصول پنج‌گانه SOLID رعایت شده‌اند:

### ۱. اصل تک‌مسئولیتی (Single Responsibility Principle - SRP)
* **شواهد پیاده‌سازی:**
  * کلاس `SafeSpendEngine` منحصراً وظیفه محاسبات ریاضی خرج امن و شاخص‌های شتاب را انجام می‌دهد. این کلاس هیچ کدی از رابط کاربری (Compose)، سیستم پیام‌رسانی، یا پایگاه‌داده ندارد؛ بنابراین تغییرات ظاهری یا روش ذخیره‌سازی، این کلاس را تحت تأثیر قرار نمی‌دهد.
  * در سطح داده‌ها نیز معماری به دو پایگاه‌داده مجزا تقسیم شده است: `DurableDb` که صرفاً داده‌های قطعی و غیرقابل بازسازی کاربر را نگه می‌دارد، و `DerivedDb` که فقط محاسبات مشتق‌شده دفترکل را ذخیره می‌کند تا بدون ریسک از بین رفتن اطلاعات کاربر، بتوان آن را حذف و دوباره محاسبه کرد.

### ۲. اصل تفکیک رابط‌ها (Interface Segregation Principle - ISP)
* **شواهد پیاده‌سازی:**
  * در لایه ارتباط با پایگاه‌داده (Room)، به جای نوشتن یک اینترفیس بزرگ و جامع (Fat DAO) که ده‌ها متد مختلف داشته باشد، دسترسی به جداول در اینترفیس‌های کوچک و تخصصی تفکیک شده است:
    * `SmsSourceDao`: منحصراً برای ثبت و خواندن پیامک‌ها
    * `CategoryDao`: برای مدیریت برچسب‌ها و دسته‌بندی‌ها
    * `RuleDao`: برای ذخیره و بازیابی قواعد دسته‌بندی خودکار
    * `InstallmentObligationDao`: برای عملیات مربوط به وام‌ها و اقساط
  * با این تفکیک، هر ماژول یا سرویس فقط به متدهایی دسترسی دارد که دقیقاً به آن‌ها نیاز دارد.

### ۳. اصل وارونگی وابستگی (Dependency Inversion Principle - DIP)
* **شواهد پیاده‌سازی:**
  * کلاس‌های سطح بالای پروژه مانند `LedgerEngine` به جای وابستگی مستقیم به کلاس‌های خاص یا هاردکد کردن اطلاعات، وابستگی‌های خود را از طریق سازنده (Constructor Injection) دریافت می‌کنند.
  * به عنوان نمونه، دریافت لیست سرشماره‌های بانکی مازاد از طریق یک ارائه‌دهنده انتزاعی و تابعی (`extraBankNumbersProvider`) انجام می‌شود. این رویکرد به ما امکان می‌دهد در تست‌های واحد بدون نیاز به اجرای شبیه‌ساز اندروید یا محیط واقعی، اطلاعات ساختگی تزریق کرده و رفتار سیستم را بررسی کنیم.

## ۴. نمونه نقض یکی از اصول SOLID و راهکار اصلاح آن (پاسخ سوال ۵)

### اصل نقض‌شده: اصل باز/بسته (Open/Closed Principle - OCP)
* **محل دقیق در پروژه:** تابع `parseBankSms` در فایل `Sms.kt`
* **شرح فنی نقض:**
  در حال حاضر برای تشخیص الگوهای خاص پیامک در هر بانک، شرط‌های زنجیره‌ای درون بدنه تابع اصلی پارسر نوشته شده است:
  ```kotlin
  // کدهای فعلی در Sms.kt
  if (bank == Bank.SEPAH && text.contains("واریز گروهی")) {
      deposit = true; withdrawal = false
  }
  if (bank == Bank.TEJARAT) {
      val typeLabel = text.substringAfter("نوع تراکنش:")
      if (typeLabel.contains("واریز")) deposit = true
  }
  ```
  طبق اصل OCP، ساختار نرم‌افزار باید برای «توسعه» باز و برای «تغییر» بسته باشد. در کد فعلی، با اضافه شدن هر بانک جدید به شبکه شتاب یا هر بار تغییر متن پیامک توسط یکی از بانک‌ها، برنامه‌نویس باید فایل اصلی پارسر را باز کرده و بدنه تابع مرکزی را تغییر دهد. این تغییر مداوم می‌تواند روی عملکرد پیامک سایر بانک‌ها اثر نامطلوب بگذارد و باگ ایجاد کند.

### راهکار اصلاحی معماری (Refactoring با الگوی طراحی Strategy)
برای اصلاح این نقض، رفتار اختصاصی هر بانک را در کلاس‌های استراتژی مجزا کپسوله می‌کنیم:

#### ۱. تعریف اینترفیس استراتژی انتزاعی:
```kotlin
interface BankSmsParserStrategy {
    fun canHandle(bank: Bank): Boolean
    fun parseCustom(body: String, base: BankSms): BankSms
}
```

#### ۲. پیاده‌سازی کلاس‌های استراتژی جداگانه برای هر بانک:
```kotlin
class SepahParserStrategy : BankSmsParserStrategy {
    override fun canHandle(bank: Bank) = bank == Bank.SEPAH
    override fun parseCustom(body: String, base: BankSms): BankSms {
        if (body.contains("واریز گروهی")) {
            return base.copy(delta = base.amountRial?.toDouble())
        }
        return base
    }
}

class TejaratParserStrategy : BankSmsParserStrategy {
    override fun canHandle(bank: Bank) = bank == Bank.TEJARAT
    override fun parseCustom(body: String, base: BankSms): BankSms {
        val type = body.substringAfter("نوع تراکنش:", "")
        val isDeposit = type.contains("واریز") || type.contains("بازپرداخت")
        val isWithdrawal = type.contains("برداشت") || type.contains("خرید")
        val delta = when {
            isDeposit && !isWithdrawal -> base.amountRial?.toDouble()
            isWithdrawal && !isDeposit -> -(base.amountRial?.toDouble() ?: 0.0)
            else -> base.delta
        }
        return base.copy(delta = delta)
    }
}
```

#### ۳. بسته شدن موتور اصلی پارسر نسبت به تغییر:
```kotlin
class BankSmsParserEngine(
    private val strategies: List<BankSmsParserStrategy>
) {
    fun parse(sender: String, body: String): BankSms? {
        val bank = bankOf(sender) ?: return null
        val base = parseCommon(bank, sender, body)
        val strategy = strategies.firstOrNull { it.canHandle(bank) }
        return strategy?.parseCustom(body, base) ?: base
    }
}
```

* **نتیجه بازآرایی:** با اعمال الگوی Strategy، کلاس اصلی پارسر هرگز برای افزودن بانک جدید دستکاری نمی‌شود (بسته به تغییر). هر زمان بانک جدیدی تعریف شود، صرفاً یک کلاس تازه پیاده‌سازی شده و به لیست استراتژی‌ها پاس داده می‌شود (باز به توسعه).
